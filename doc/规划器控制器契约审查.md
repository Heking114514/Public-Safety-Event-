# 规划器与控制器契约审查记录

记录日期：2026-10-10（北京时间）  
任务边界：只记录 `new_map_planner`、`visual_navigation` 之间的接口和行为证据；本轮不修改生产代码，不修改仿真器。

## 结论摘要

规划器和控制器之间确实存在契约不完整，但不能简单归纳为“45 道刚性门禁”。当前最重要的三个问题是：

1. 障碍恢复后的姿态没有通过明确的恢复模式传给规划器。普通规划入口会拒绝“车头方向与正向道路不一致”或“正向段被阻挡”的起点。
2. 路线元数据仍通过 `Pose.position.z` 的毫米值兼容编码传递，功能可用但接口脆弱。
3. 规划器的转弯检查主要是几何可行性，控制器还叠加了实时位姿、预测前瞻、微调和进度看门狗；两者没有统一的动态执行能力模型。

“路线规划耗时导致 W0 落后”和“转弯上下文被轻微定位更新清空”目前只能判定为风险，不能作为已证实根因。

## 评审意见逐项核实

### 1. 障碍恢复后无法以当前姿态重新规划

判定：**基本属实，高优先级**。

`new_map_planner/src/planner.cpp` 的 `start_seeds()` 会检查：

- 起点 footprint 是否安全；
- 起点是否在道路附近；
- 起点航向是否接近离散道路航向；
- 起点到前方道路节点的正向段是否无碰撞。

正向段被阻挡时返回 `START_FORWARD_BLOCKED`；只有反向可行时会记录 `START_REQUIRES_REVERSE`，不会自动生成普通倒车起步路线。

因此，控制器“沿历史轨迹倒退到安全位置”与规划器“从当前姿态开始正常规划”之间缺少明确协议。当前实现没有正式的 `recovery_start`、`reverse_start` 或 `recovery_anchor` 字段。

但这不等于每次障碍恢复都会死锁。控制器通常先尝试历史轨迹恢复，只有恢复结束后才请求规划器；是否死锁取决于恢复后的姿态和规划请求内容。

### 2. Z 轴毫米标记

判定：**属实，但风险描述有夸大**。

规划器在 `new_map_planner/src/node.cpp::MakePath()` 中使用以下兼容编码：

| Z 值 | 含义 |
|---:|---|
| `0.001` | 普通转弯 |
| `0.002` | 倒车到达转弯 |
| `0.003` | RFID 超节点 |
| `0.004` | RFID 转弯 |
| `0.005` | RFID 倒车转弯 |

控制器在 `visual_navigation/include/visual_navigation/route_manager.hpp::LoadPath()` 中反解，容差为 `1e-6`。

当前正式地图配置 `arena.yaml` 中 `publish_shunt_markers: true`，所以不是默认关闭。ROS 消息使用 `float64`，正常链路不会无缘无故产生微米级随机误差；真正的风险是中间节点重建 Path、忘记复制 Z 值，或发布者使用了不同的标记协议。

长期应改为明确的路线元数据字段，避免继续扩展 Z 轴协议；短期必须保留兼容解析并增加发布/接收契约测试。

### 3. 规划时延导致 W0 落后

判定：**代码路径存在，最近 bag 未能证明它是本次失败根因**。

规划请求以请求时起点生成第一个 waypoint。路线激活前车辆如果继续运动，W0 可能不再位于车体当前位置。

控制器只在 `SatisfiedRouteStartMayAdvance()` 判断当前位置仍在 W0 容差内时消费第 0 点，否则会继续以 W0 为当前目标。若 W0 已经落到车后方，确实可能产生反向路径误差。

但控制器还会经过路径投影、路口标记、航点停止属性和 `pathError` 恢复判断，因此不能直接断言会必然触发 90 度错误或立即倒车。

最近 08:09 bag 中，第二路线加载后立即进入 `BRAKING_AT_WAYPOINT`、`TURN_ENTRY_CHECK`，没有出现明显的追逐历史 W0 日志；本包不足以确认该问题。

### 4. 刹车后转弯上下文丢失

判定：**评审原描述不准确，存在较弱的上下文管理风险**。

`RunBrake()` 会在 `AdvanceWaypoint()` 前保存：

- `stoppedTurnGeometryHeading_`；
- `stoppedTurnArrivalHeading_`；
- `stoppedTurnTargetHeading_`；
- `stoppedAtPlannedTurn_`。

普通 `ResetManeuver()` 不会清除 `stoppedAtPlannedTurn_`；清除主要发生在完整运行重置、转弯完成、障碍恢复或路线替换。因此，单次轻微定位更新不会直接抹掉转弯上下文。

风险在于这些字段分散在导航器成员变量中，而不是一个带路口 ID 的不可变动作上下文。路线替换、恢复和任务重置可能同时清空它们，后续应增加状态迁移契约测试。

### 5. 规划器几何可行、控制器动力学不可执行

判定：**部分属实，是长期架构问题**。

规划器已经使用车辆长宽、道路宽度、footprint、转弯扫掠和安全余量；不能说规划器只看抽象图连通性。

但规划器没有把以下因素作为路线代价或可执行性模型：

- 电机死区与响应延迟；
- 轮胎打滑和地面摩擦；
- 实际控制周期抖动；
- 实车定位残差；
- 连续窄弯的历史失败率。

所以 `sweep_is_free()` 证明的是几何扫掠可行，不是实车一定能够稳定执行。

## 当前问题优先级

### P0：已由最近 bag 直接证实

### P1：代码已证实、最近 bag 尚未单独复现

- 普通规划入口不支持显式“倒车姿态起步”；
- Z 轴兼容标记是脆弱的隐式协议；
- 规划器没有使用实车动态失败率修正转弯代价。

- 规划时延是否让 W0 落到车后方并引起错误反向跟踪；
- 路线替换、定位校正或障碍恢复是否在某个具体时序中清空转弯上下文；
- 规划器扫掠模型与实车 footprint、轴心偏移是否完全一致。

## 后续核实实验

1. 在路线输入和当前位姿上记录 W0 距离、路径投影纵向距离、W0 是否位于车后方。
2. 对每次 `TURN_NEED_REPLAN` 记录请求姿态、footprint 碰撞角点、最近道路段和规划失败原因。
3. 用同一入口分别测试：正常规划、显式恢复规划、历史轨迹倒退后规划，比较三者的起点契约。
4. 将规划器输出的转弯 metadata 与控制器解析结果逐点对照，确认不存在 Z 标记丢失。
5. 只有上述证据完整后，才决定是否引入恢复模式接口或更换 Path 元数据协议；不先放宽安全门。

## 待审核解决方案

本节是下一轮修改方案，当前只用于审核，尚未修改生产代码。

### 修复原则

1. 不通过放宽 `footprint`、道路边界或起点碰撞检查来掩盖问题。
2. 转弯动作失败时，控制器必须保持在已知安全姿态，不能继续用同一套被拒命令反复尝试。
3. 规划器收到恢复请求时，必须知道这是正常起步还是障碍/转弯失败后的恢复起步。
4. 所有新行为先在隔离核心和契约测试中验证，再接入生产节点。
5. 一次只改一个契约边界，保留原有普通路线和障碍恢复接口的兼容行为。

### P0：修复转弯失败后的姿态漂移

#### 当前问题

最近 08:09 rosbag 显示，`corner_arc_command` 连续因为
`footprint_outside_envelope` 被拒后，控制器仍然重复进入 `TURN_TRIM_SEARCH` 和
`TURN_REVERSE_TRIM`。第 6 次尝试耗尽后，车辆已经不再处于稳定的路口入口，随后规划器报告
`START_POSE_COLLISION`。

#### 修改方案

在 `TurnManeuverController` 增加一次性的失败结果上下文，不新增一层永久门控：

1. 每次圆弧命令被安全检查拒绝时，记录拒绝时的实测 pose、geometry heading、目标出口方向、
   拒绝原因和当前 trim attempt。
2. 同一入口在一次微调周期内，如果拒绝原因、预测采样和入口局部位置没有改善，不再继续
   发送相同方向的 trim；直接返回 `TURN_NEED_REPLAN`，保持零速。
3. `TURN_NEED_REPLAN` 返回前保存一个 `recovery_pose`，该 pose 必须是最后一次通过
   `pose_is_safe` 的实测姿态，而不是失败预测姿态。
4. 如果当前实测姿态已经离开道路安全包络，控制器只发布零速并请求恢复，不再继续前后微调。
5. 清晰区分三种结果：
   - `RUNNING`：仍在改善并且当前姿态安全；
   - `NEED_REPLAN`：当前动作无法继续，但姿态仍可作为恢复起点；
   - `FAULT`：实测姿态已经无法确认安全，必须保持任务。

#### P0 验收条件

- 相同 `footprint_outside_envelope` 输入最多只尝试一次无改善的 trim，不再连续重复 6 次；
- 失败后 `/cmd_vel_nav` 为零速，且日志包含最后安全 pose；
- 失败姿态请求规划时，规划器不会把控制器继续微调后的越界姿态误认为正常路线起点；
- 正常可通过转弯的现有测试命令和实车 bag 行为不变。

### P0：定义恢复规划起点契约

#### 当前问题

普通 `PlanRequest` 只包含起点 pose 和目标，无法表达“这是转弯动作失败后的恢复请求”。规划器
因此只能按正常起步规则检查航向和正向道路，无法决定是否允许沿当前道路反向离开路口。

#### 修改方案

优先复用现有 ROS 接口边界，增加恢复语义而不是改变普通规划规则：

1. 在规划请求中增加可选恢复字段，最小集合为：
   - `start_mode`: `NORMAL` / `TURN_RECOVERY` / `OBSTACLE_RECOVERY`；
   - `anchor_node_id` 或明确的 `recovery_anchor`；
   - `allow_reverse_departure`；
   - `incoming_lane_id`（如果已知）。
2. `NORMAL` 请求保持现有 `start_seeds()` 行为，不允许因为恢复需求而放宽普通起步门禁。
3. `TURN_RECOVERY` 只允许从最后安全 pose 或已知道路段出发，优先生成沿来向道路退离路口的
   恢复段；恢复段通过同一 footprint 和道路碰撞检查。
4. `OBSTACLE_RECOVERY` 继续使用现有历史轨迹恢复逻辑；只有恢复控制器确认到达锚点后，才提交
   普通规划请求。
5. 若恢复段也不可行，返回结构化失败原因和建议动作，不再把失败统一包装成普通
   `START_POSE_COLLISION`。

#### P0 验收条件

- 正常路线不会因为新增字段改变规划结果；
- 转弯失败后，规划器能明确区分“请求继续倒退”和“请求重新规划”；
- 车头朝向障碍但车尾道路可退时，不会直接陷入普通规划起步拒绝；
- 恢复方向仍必须通过 footprint、道路边界和动态障碍检查。

### P1：替换 Z 轴隐式路线标记

不在 P0 中修改，避免与转弯失败修复同时引入协议迁移风险。

方案是为 `RoutePlan` 增加显式 waypoint metadata：

- `turn_junction`；
- `reverse_arrival_turn`；
- `rfid_supernode`；
- `geometry_heading`；
- 可选 `junction_id`。

过渡期同时发布显式字段和 Z 轴兼容标记；控制器优先读取显式字段，旧路线仍可用 Z 轴解析。
待实车和仿真验证通过后，再移除旧编码。

### P1：处理路线激活时序和 W0

暂不直接跳过第 0 点，而是增加路线激活诊断：

1. 记录路线发布时 pose、路线激活时 pose、W0 距离和路径投影纵向距离。
2. W0 已被安全越过时，只消费 W0，不改变后续转弯 marker 授权。
3. W0 是转弯 marker 时，消费动作必须保留 `routeStartTurnAuthorized`。
4. W0 位于车后且无法安全消费时，返回结构化 `ROUTE_START_STALE`，请求规划器基于最新 pose
   重新编译路线，而不是让 Stanley 追踪落后的 W0。

### P2：统一规划器与控制器的可执行性模型

规划器继续负责几何可行性，控制器继续负责实时闭环，不把控制器状态机复制到规划器。新增
可测量的转弯代价和失败统计：

- 入口横向偏差；
- 入口航向残差；
- trim 次数；
- 最近一次安全拒绝原因；
- 实车完成时间和最大横向误差。

这些数据只用于路线代价和测试筛选，不直接变成新的运行时硬门控。规划器不能选择几何可行但
历史上高失败率的转弯，除非没有其他可行路线。

### 实施顺序

1. 先新增 P0 的转弯失败上下文和隔离单测，不改 ROS 接口。
2. 用 08:09 bag 的入口姿态做离线重放，确认不会重复发送被拒圆弧命令。
3. 接入 `TURN_NEED_REPLAN` 的结构化恢复请求，补规划器/控制器契约测试。
4. 仿真只验证关键转弯和恢复路径，不作为实车动态通过的替代证据。
5. 新实车 bag 至少验证两次同一路线，再决定是否进入 P1 协议迁移。

### 明确不做的修改

- 不把所有 `footprint_outside_envelope` 改成允许；
- 不扩大道路边界或删除起点碰撞检查；
- 不让普通节点获得无条件倒车或原地掉头能力；
- 不把 RFID 航向校正混入转弯 geometry heading；
- 不在本轮同时重写全局规划搜索和底盘控制器。
