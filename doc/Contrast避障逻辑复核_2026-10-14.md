# Contrast 避障逻辑复核

复核日期：2026-10-14（Asia/Shanghai）。对照《避障动作设计与当前实现差异记录.md》第 5、6、10、11、12 节，检查当前工作区源码和配置。本次只增加复核记录，没有修改控制代码或控制参数。

**结论：Contrast 是局部导航执行层，但现有实现只完成了部分恢复流程，不能认定符合文档全部规则。文档第 12 节“已经完成本记录定义的恢复动作改造”和历史测试全通过的结论，不能代表当前工作区。**

`contrast_controller` 提供 ROS 可执行入口和固定转弯动作；实际路线跟随、障碍分类、恢复候选与恢复状态机在它链接的 `contrast_navigation_core` 中。总控与全局规划分别由 `navigation_mission_manager`、`new_map_planner` 承担。

## 1. 当前最基本的恢复场景也没有通过（P1，已实测）

重新构建两个 Contrast 包后，运行现有正式地图场景 `south_nominal`：候选 2 被选中，目标道路为 `ROAD_X1_Y2`，车辆完成倒车到点、换向停车和固定转弯交接，但转弯到 `(1.272, -0.530, -0.722 rad)` 时报告 `FAULT_POSE_RECOVERY_STRICT_TURN_SWEEP`。总控随后进入 FAULT，没有恢复完成和后续直行证据。

这次是控制器扫掠检查主动拒绝危险运动，不能据此说车辆实际发生了碰撞；但这个基础场景目前确实无法完成恢复。

同时，现有 `turn_maneuver_test` 中 `FullLeftAndRightAtLaunchWithRealOutputAndCollision` 左右两种方向均没有完成：停在 `TURN_60`，返回 `NEED_REPLAN`，测试模型各累计 60 次碰撞保护拒绝。其他 4 个 C++ 用例通过，两个 Python 注册测试通过，即 CTest 为 **2/3**，不是文档记录的 3/3。

相关实现：

- [pose_recovery.cpp:209](../src/contrast_navigation_core/src/pose_recovery.cpp#L209)：`plan()` 只检查起点、锚点和候选终点，随后固定填入三个阶段，没有验证整套动作能通过。
- [pose_recovery_control.cpp:271](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L271)：实际执行时才拒绝不安全转弯。
- [turn_maneuver_test.cpp:221](../src/contrast_controller/test/turn_maneuver_test.cpp#L221)：现有左右转弯碰撞测试。

修正方向：先定位当前参数和车身几何下固定转弯轨迹被拒绝的原因；候选接受前应验证该模板实际可执行，不能把三个静态位姿安全等同于整条动作安全。本次没有调整参数，也没有确定失败最初由哪次历史修改引入。

## 2. T 掉头、X 反向出口只有候选名称，没有两次转弯动作（P1，源码与探针确认）

文档要求 T-U / X-REVERSE 经过“第一次转入旁支 → 到第二转弯点 → 停车 → 第二次转弯 → 返回反方向”。当前所有候选都使用同一套 `RETREAT_TO_TURN_POINT → ALIGN_FOR_TURN → TURN_INTO_EXIT`，没有中间旁支、第二转弯点或第二次转弯状态。

- [pose_recovery.cpp:153](../src/contrast_navigation_core/src/pose_recovery.cpp#L153) 会生成 `t_junction_reverse` / `x_junction_reverse`。
- [pose_recovery.cpp:214](../src/contrast_navigation_core/src/pose_recovery.cpp#L214) 对所有模板生成相同三个阶段，不根据 `template_id` 组织动作。
- [pose_recovery_control.cpp:203](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L203) 在车辆已倒车到路口之后，才拒绝大于 2.55 rad 的转角。

直接调用当前源码，在正式地图上得到 `x_junction_reverse / TUNNEL_3`，`plan()` 返回成功、三个阶段、转角 π；该角度随后必然触发 `FAULT_POSE_RECOVERY_UNSUPPORTED_TURN`。局部规划成功会让选择服务先返回 success，总控不再按“选择失败”尝试其他候选。

修正方向：实现两个明确的转弯子动作及其借用道路、停车点；在完整实现前，应在候选生成或选择服务中拒绝当前执行不了的模板，不能先倒车后才发现模板不支持。临时过滤只能消除协议错误，不能算满足文档的掉头要求。

## 3. 转弯中遇障仍会中断当前动作（P1，源码确认）

文档 S3 要求先安全完成当前 90° 转弯，到转后转弯点停车，再倒车转回原车道，并按 T 规则处理。

当前异常障碍路径为：

`ClassifyPendingObstacle → BeginObstacleRecovery → BeginPoseRecovery → ResetManeuver`。

- [obstacle_recovery.cpp:276](../src/contrast_navigation_core/src/obstacle_recovery.cpp#L276)：判为异常后直接启动恢复。
- [pose_recovery_control.cpp:123](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L123)：没有保存专用原转弯上下文，直接重置动作。
- [navigation.cpp:138](../src/contrast_navigation_core/src/navigation.cpp#L138)：重置实际清空固定转弯控制器。

因此不存在文档定义的“完成当前转弯 → 倒车转回原路 → T 恢复”专用链。

现有 `after_normal_90deg_turn` 不是该场景的覆盖证据：[run_pose_recovery_scenarios.py:436](../src/contrast_controller/scripts/run_pose_recovery_scenarios.py#L436) 明确等待 `FOLLOWING`、正常转弯完成确认和实测前进后，才注入障碍。它验证的是**转弯后直行遇障**。

## 4. 长距离倒车仍被 0.85 m 半径直接挡住（P1，源码与探针确认）

[pose_recovery.cpp:133](../src/contrast_navigation_core/src/pose_recovery.cpp#L133) 在候选生成阶段直接判断“当前位姿到锚点距离大于 `config_.max_radius` 则无候选”；当前 YAML 为 0.85 m。调用方随后报 `FAULT_POSE_RECOVERY_NO_EXIT`。

最小探针使用正式地图，在当前位姿安全、距锚点 0.86 m 时得到 0 个候选；同一几何仅在探针内部把半径改为 2 m，得到 3 个候选。这证明半径门槛仍实际生效。探针没有修改项目参数，也不代表已经验证这些候选的完整运动轨迹。

该逻辑直接违反文档 S4 的“不因固定局部半径直接误报无候选”。当前也没有沿道路拓扑回溯到更早合法 T/X 路口的过程。

## 5. 恢复运动期间的新障碍没有进入扫掠检查（P1，源码确认）

一次恢复锁存原障碍是正确的，但还需要处理恢复途中新增障碍或道路阻塞。

- [obstacle_recovery.cpp:7](../src/contrast_navigation_core/src/obstacle_recovery.cpp#L7)：恢复阶段收到新的前方 Bool，只更新缓存后返回。
- [pose_recovery_control.cpp:47](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L47)：新多边形仅写入 `latestRecoveryPolygon_`。
- [pose_recovery.cpp:102](../src/contrast_navigation_core/src/pose_recovery.cpp#L102)：扫掠检查所用 `dynamic_` 在生成候选时锁存。
- [pose_recovery.cpp:196](../src/contrast_navigation_core/src/pose_recovery.cpp#L196)：选择时再加入当时的阻塞道路快照，之后没有更新入口。
- [pose_recovery_control.cpp:222](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L222)：恢复转弯输入的 `obstacle_blocked` 固定为 false。

所以“每个周期重新扫掠”目前是对旧障碍快照重新扫掠，不能证明会对新出现的障碍停车。`poseRecoveryRevision_` 每次恢复置 0，执行中也没有消费新的障碍版本。总控的版本校验不能代替执行层对当前危险的检查。

修正方向：保留原恢复事务的锁存几何，同时增加新危险触发停止/作废当前执行的路径；不能简单清掉原障碍或把所有前方 true 都当作新障碍。

## 6. 完成时没有确认真实出口道路（P1，完成判据探针确认）

文档要求实际 pose 位于目标道路安全包络、实际车道等于目标车道，之后才能报告完成。

- [turn_maneuver.cpp:317](../src/contrast_controller/src/turn_maneuver.cpp#L317)：最终只检查固定 90° 航向误差和局部 `abs(x)` 横向门限，不检查目标出口方向上的纵向位置、道路 ID 或候选出口距离。
- [pose_recovery_control.cpp:225](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L225)：固定动作返回 COMPLETED 后直接跳过余下步骤。
- [pose_recovery_control.cpp:179](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L179)：停车后直接报告恢复完成。
- [pose_recovery_control.cpp:120](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L120)：`resume_lane` / `resume_node` 直接复制选中候选；只有 pose 与航向取实际值。

最小完成判据探针按阶段喂入位姿：目标为局部 +y 出口，但最终实际 pose 为 `(0.013, -0.177483, π/2)`，位于路口另一侧，仍返回 COMPLETED。这个探针证明缺少出口侧检查，**不是声称完整真实闭环已产生该轨迹**。

总控检查 `safe_pose.yaw` 与 `resume_heading`，但控制器将二者同时填写为当前 yaw，因此这个一致性检查也不能代替与选定目标航向/目标道路的比较。

修正方向：在完成前以地图目标车道做投影和全车身包络验证，同时检查出口侧纵向进度、中心误差及目标航向；验证失败保持停车并报告结构化失败。

## 7. 停车确认使用缓存值，且部分等待没有失败时限（P2，源码确认）

[pose_recovery_control.cpp:153](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L153)、[174](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L174)、[310](../src/contrast_navigation_core/src/pose_recovery_control.cpp#L310) 的停止确认只检查已等待时间和缓存的左右轮速，不检查遥测是否收到、是否新鲜或是否连续停止。轮速成员默认是 0；而所复用固定动作的 CAPTURE 仅捕获上下文并等待两次 update，没有额外的实际停止检查。

反过来，如果缓存轮速一直高于阈值，这些分支会持续 return；部分等待在动作超时检查之前，没有停车失败截止时间。因此既可能把无新鲜证据的缓存当停车，也可能无限等待，不能宣称已完整满足“确认停止”和“有限失败”的要求。

应复用已有独立轮速停止证据、新鲜度和连续样本机制，给每次停车确认设独立失败时限。

## 已确认存在的正确基础

- Contrast 链接自己的导航核心，局部动作实现与生产 `visual_navigation` 核心分开。
- 障碍恢复中使用实时里程计计算目标误差，倒车到点需要位置与航向同时达标。
- 倒车/前进调整切换会发零速度；前进调整最多尝试一次。
- 已调用唯一固定转弯控制器，实际非零恢复命令有车身扫掠检查。本次基础场景就是由该检查安全拒绝。
- 选择服务有恢复 ID、障碍版本及出口/借用道路检查；总控候选评估使用 `activate=false`，完成后从实际 pose 重新规划，普通节点计数归零。

这些说明实现并非完全错误，但不能替代缺失的完整拓扑模板、转弯中恢复、长距离恢复、新危险处理和真实出口验证。
