# 避障动作设计与当前实现差异记录

记录时间：2026-10-13（Asia/Shanghai）  
文档状态：Contrast 实现与验收记录  
适用范围：`contrast_controller`、`contrast_navigation_core` 以及它们与现有 `navigation_mission_manager`、`new_map_planner`、`vehicle_loopback_sim` 的恢复动作接口

## 1. 文档目的

这份文档记录当前系统已经完成的任务管理、RFID、路线规划和障碍锁存能力，并单独审查避障动作本身是否符合已经确定的道路拓扑规则。

当前结论是：

> 原记录指出的通用局部姿态搜索问题已经在 Contrast 侧完成改造。`contrast_navigation_core` 现在按地图道路拓扑生成带 `t_junction_*` 或 `x_junction_*` 语义的恢复候选，并按“倒车到合法路口点 → 停车确认 → 闭环回中 → 进入出口道路”的阶段执行。控制器每个周期使用融合里程计重新计算目标位置、道路中心误差和航向误差，并对当前命令和短时域进行车身扫掠检查。
>
> 本次实现和验收仅覆盖 Contrast；`visual_navigation`、任务管理器、规划器以及现有正常控制参数没有被用来掩盖恢复逻辑，也没有被改写。六个独立 ROS 域 loopback 场景全部通过，包括正常 90° 转弯后再遇障碍的场景。

本记录只定义问题、目标行为、接口边界和验收标准。本阶段不修改两个已有控制器的调参参数，也不修改生产控制器和 Contrast 控制器的正常直行、正常转弯参数。

本轮实现范围进一步收窄为：

- 只修改 `contrast_controller` 和它使用的 `contrast_navigation_core`；
- 只重写 Contrast 侧的障碍恢复动作、恢复动作状态和必要的 Contrast 侧执行胶水；
- 保留 `navigation_mission_manager`、`new_map_planner`、RFID 流程、任务三层逻辑和全局路线评估；
- 保留 `visual_navigation` 生产控制器及其正常直行、正常转弯实现；
- 不通过修改生产包或正常控制参数来实现避障动作。

如果 Contrast 侧现有消息字段不足，优先在 Contrast 包内部使用已有接口完成动作；只有确实无法表达恢复动作时，才提出最小接口兼容方案，并在实现前单独记录，不能顺手改动任务管理器和规划器。

## 2. 现有系统职责

当前系统的职责边界如下：

```text
视觉/测距模块
    │
    │ 障碍物位置、距离、前方阻塞信号
    ▼
navigation_mission_manager
    │  障碍锁存、阻塞边、任务进度、候选出口评估、全局重规划
    ▼
visual_navigation 或 contrast_navigation_core
    │  路线跟随、正常转弯、避障局部运动执行
    ▼
/cmd_vel_nav
```

### 2.1 `navigation_mission_manager`

总控当前已经负责：

- 接收控制器报告的真实障碍多边形；
- 为一次恢复建立 `recovery_id` 和障碍版本；
- 保存障碍发生前已经完成的 DRIVE、RFID 和任务进度；
- 将物理阻塞边加入 `blocked_lane_ids`；
- 清除被障碍中断的旧路线，防止旧路线继续接管；
- 对控制器提供的恢复候选出口逐个进行只读全局规划评估；
- 选择一个在当前任务阶段仍可继续的候选；
- 等待控制器报告真实恢复出口后重新发布正常路线；
- 让后续规划继续执行当前任务层，而不是把恢复动作当成已经完成的任务路线。

恢复流程的关键阶段是：

```text
FOLLOWING / EXECUTING
    -> OBSTACLE_BRAKING
    -> POSE_RECOVERY_BRAKING
    -> POSE_RECOVERY_SELECTING
    -> planning_motion
    -> motion
    -> POSE_RECOVERY_COMPLETE
    -> 全局 REPLANNING
    -> WAIT_ROUTE_ACK
    -> FOLLOWING
```

`planning_motion` 表示控制器已经开始执行本地恢复搜索。它不表示全局路线已经执行完，也不表示避障动作已经符合特定路口规则。

### 2.2 `new_map_planner`

全局规划器当前负责：

- 根据当前任务阶段、已完成任务、已覆盖道路、隧道状态和返航条件生成后续路线；
- 处理动态障碍和被阻塞道路；
- 通过普通节点计数约束路线；
- 评估恢复候选出口之后是否还能完成当前任务；
- 生成恢复完成后的正常前进路线。

全局规划器不应该负责控制车辆如何倒车、如何通过一个丁字路口、如何执行两次特定转弯。避障动作属于控制器执行层，规划器只负责判断恢复出口之后的任务路线是否可行。

### 2.3 `visual_navigation` 和 `contrast_navigation_core`

正常控制器已经具有：

- 路线航点跟随；
- 正常停车和 90 度转弯；
- 转弯入口和车身扫掠安全检查；
- 障碍检测后的刹停和障碍多边形锁存；
- 局部姿态恢复搜索；
- 恢复完成后的实际出口报告。

`contrast_controller` 当前链接独立的 [`contrast_navigation_core`](../src/contrast_navigation_core/README.md)。它与 [`visual_navigation`](../src/visual_navigation/README.md) 的正常控制接口已经隔离，但两边的当前姿态恢复算法仍然是同一类通用局部搜索。因此，包已经隔离并不等于避障动作已经换成了新的路口恢复策略。

## 3. 已确认符合的设计要求

### 3.1 障碍检测后停车并锁存

控制器检测到前方障碍后会进入刹停确认，确认障碍数据仍然新鲜后锁存障碍几何。总控随后将这次障碍与恢复标识、障碍版本绑定。

旧路线会被清除，旧的候选响应和旧的障碍状态不会直接驱动新一轮恢复。控制器的恢复选择服务也会检查：

- `recovery_id`；
- `obstacle_revision`；
- 候选编号；
- 出口车道是否仍然被阻塞；
- 候选借用的车道是否仍然被阻塞。

这一部分解决的是恢复事务的一致性，当前实现基本符合要求。

### 3.2 阻塞车道会进入全局规划约束

当前控制器会根据障碍几何和地图车道关系确定 `blocked_lane_id`，总控将其加入阻塞集合，并让全局规划器在后续路线中避开该物理边。

恢复完成后，阻塞的普通边保持为 skipped，不会被伪造为 covered。未完成的任务点、隧道和其他尚未确认的道路仍然保持未完成状态。

当前仍需要在后续实现中把“阻塞边推断”从几何近邻结果提升为明确的道路拓扑结果，见第 6 节。

### 3.3 RFID 停车和位置校正

当前任务管理器的 RFID 流程已经包含：

1. 检测到当前路线期望的 RFID；
2. 请求保持车辆停止；
3. 等待车辆速度和位置稳定；
4. 调用地图位置校正服务；
5. 等待校正后 `x/y` 位置收敛；
6. 在第一任务层对第一次到达的任务点播报；
7. 保持约定的停车时间后确认 RFID 检查点；
8. 释放停止保持并继续路线。

当前配置中的 `rfid_stop_duration_s` 为 1 秒。校正使用任务点的地图位置，校正的是位置，不通过 RFID 流程强制修改车身姿态。

相关实现见：

- [`mission_manager.yaml`](../src/navigation_mission_manager/config/mission_manager.yaml)；
- [`rfid.cpp`](../src/navigation_mission_manager/src/rfid.cpp)；
- [`planning.cpp`](../src/navigation_mission_manager/src/planning.cpp)。

### 3.4 两个普通节点之后经过超节点

全局覆盖规划器已经使用普通节点计数约束路线。当前计数逻辑的含义是：

```text
到达 RFID 任务超节点：ordinary_count = 0
经过普通节点：ordinary_count += 1
ordinary_count == 2 时，后续必须进入任务/超节点
```

恢复动作本身不应被当成覆盖道路，也不应因为局部搜索经过某个几何点就自动增加任务进度。恢复完成后，总控从真实恢复出口重新规划，并从恢复后的正常前进状态开始计算后续普通节点。

这一部分属于全局规划和任务交接，当前基本符合设计。但当前局部恢复动作自身没有 RFID 检查点逻辑，也没有普通节点语义，因此不能让局部搜索直接穿过任务点后冒充正常路线已经完成任务。

### 3.5 任务三层结构基本保留

当前任务管理器和全局规划器已经保留以下任务顺序：

1. 第一层：访问并播报所有 RFID 任务点；
2. 第二层：遍历所有隧道；
3. 第三层：遍历所有未访问且未被阻塞的道路，最后回到起点。

障碍发生时，当前系统会保存已完成的任务证据和道路进度，未确认的任务不会因为路线已经开始就被标记完成。恢复后的全局规划会继续当前层，并使用阻塞边约束后续路线。

因此需要改造的是局部避障动作，不应重新改写这三层任务逻辑。

## 4. Coding 前的避障动作基线

以下行为描述记录本次改造前的 Contrast/生产共用姿态恢复逻辑，用于保留问题证据；改造后的实际行为见第 12 节和验收报告。

Coding 前 `PoseRecovery` 的主要流程是：

1. 找到距离障碍物较近的地图车道；
2. 根据车辆当前姿态选择一个锚点端点；
3. 找到与锚点相连的候选车道；
4. 为每条候选车道生成一个出口位姿；
5. 使用带碰撞检查的前进/倒车直线和弧线 primitive 搜索安全动作序列；
6. 控制器执行搜索结果；
7. 到达候选出口后报告 `resume_node`、`resume_lane` 和当前航向。

当前候选模板是通用的：

```text
junction_pose_forward_reverse
```

它没有在数据结构中明确记录：

- 丁字路口还是十字路口；
- 当前进入的道路是哪一条；
- 障碍所在边的方向；
- 最近的合法转弯点；
- 这是 90 度转入、掉头返回还是十字路口换道；
- 一个恢复动作需要一次还是两次特定转弯；
- 是否来自“正常 90 度转弯中发现障碍”的特殊场景。

局部搜索虽然允许正向和反向 primitive，但这不等于已经实现了“长距离倒车到路口，再执行特定转弯”。当前搜索的方向切换是几何搜索结果，不是道路拓扑动作结果。

## 5. 与用户确定规则的差异（Coding 前基线）

### 5.1 两种基本动作没有成为避障动作的硬约束

用户确定的运动语义是：

1. 直行；
2. 特定转弯。

当前局部恢复搜索实际使用的是一组几何 primitive，包括：

- 正向直线；
- 反向直线；
- 带角速度的正向弧线；
- 带角速度的反向弧线；
- 搜索过程中的方向切换。

这些 primitive 可以作为底层执行手段，但上层没有把它们组成具有道路含义的动作。例如，当前代码没有一个明确的 `RETREAT_TO_TURN_POINT`、`TURN_INTO_BRANCH` 或 `TURN_BACK_TO_ORIGINAL_LANE` 状态。

因此，即使某次搜索生成的轨迹在几何上能够到达出口，也不能证明它执行了用户要求的特定转弯序列。

### 5.2 长距离倒车没有真正实现

当前姿态恢复配置中存在：

```yaml
recovery_max_radius: 0.85
```

恢复搜索要求车辆当前位姿和锚点之间的距离在这个范围内，并且搜索状态不能越出局部半径。因此当前 active pose recovery 的实际行为是有限距离的局部姿态调整。

当障碍物距离下一个路口较远时，当前代码可能无法生成候选，而不是持续倒车到下一个路口转弯点。旧的历史轨迹退回链可以追加固定距离退车，但它是历史 breadcrumb 恢复机制，不能代替基于路口的长距离倒车，也不能证明已经到达正确转弯点。

目标行为应当是：

```text
障碍只发生在当前边上
    -> 沿当前边反向行驶
    -> 连续倒车到合法路口转弯点
    -> 在该点停车确认
    -> 执行特定转弯动作
```

倒车距离应由地图中的路口转弯点决定，而不是由固定局部半径决定。实际倒车仍然必须逐段进行车身扫掠检查、障碍距离检查和无进展检查。

### 5.2.1 倒车结束后的姿态回中是必需的闭环阶段

倒车到转弯点的过程中，车辆可能因为定位误差、车道边缘、车身偏角、底盘执行误差或障碍物位置而没有始终保持在道路中心。到达倒车目标附近并不等于已经具备转弯条件。

因此，倒车恢复必须把“到达路口附近”和“达到可转弯姿态”分成两个判据：

```text
到达路口转弯点附近
    -> 检查道路横向误差、纵向误差和航向误差
    -> 姿态已经适合转弯：直接进入特定转弯动作
    -> 姿态没有适合转弯：进入闭环回中/入位阶段
    -> 达到转弯入口判据后停车确认
    -> 开始特定转弯
```

回中阶段允许两种执行方式，具体由当前安全空间和实时位姿决定：

- 在倒车过程中同时做小幅方向修正，使车身逐步回到道路中央；
- 倒车动作已经完成但车身偏离道路中央时，先短距离向前行驶，再调整到道路中心和正确进入航向。

向前回中不是固定必做步骤。只有当前姿态确实需要它并且前方空间安全时才执行；如果倒车过程中已经完成回中，则直接进入转弯准备。回中不能依赖预先录制的速度序列，也不能只按固定距离播放动作。

回中控制必须是基于实时反馈的闭环动作：

- 每个周期根据实际位姿重新计算道路中心误差；
- 同时约束横向误差、纵向误差和航向误差；
- 使用与正常直行一致的实际运动反馈口径；
- 每条命令都重新检查车辆全身扫掠和障碍距离；
- 方向切换前停车确认；
- 无进展、误差发散或安全包络不足时停车并结束本次恢复。

这里的“调整到道路中央”是为了让车辆以适合转弯的姿态到达转弯入口，不是简单把车辆几何中心强行投影到一条线，也不是把当前轨迹回放到某个历史点。转弯开始前必须确认车辆已经在目标道路包络内、航向与进入道路一致、横向误差满足转弯入口要求。


当前 `PoseRecovery::plan()` 会在搜索过程中自由组合正向和反向动作。它没有显式禁止：

- 在普通道路中间改变恢复方向；
- 还没有到转弯点就直接朝相邻车道转入；
- 在非路口位置通过弧线改变道路方向；
- 把一个局部几何出口当成已经完成路口动作。

目标实现需要让长距离反向动作只能从障碍恢复状态进入，并且必须有明确的终点：

```text
指定的路口 ID + 指定的转弯点 + 指定的进入方向
```

### 5.4 丁字路口没有显式模板

对丁字路口，至少需要区分以下两类动作。

#### 5.4.1 丁字路口 90 度转入另一条边

目标流程：

```text
当前边前方被阻塞
    -> 沿当前边连续倒车
    -> 到达路口另一侧的转弯点
    -> 停车确认
    -> 直行到入口并执行一次特定 90 度转弯
    -> 进入另一条可用边
    -> 恢复正常前进
```

当前代码没有 `90_DEGREE_RECOVERY_TURN` 这样的动作模板。它只会把相邻车道作为候选出口，然后交给通用局部搜索。

#### 5.4.2 丁字路口掉头后返回原来道路的反方向

目标流程：

```text
当前边前方被阻塞
    -> 沿当前边连续倒车到路口转弯点
    -> 停车
    -> 执行第一次特定转弯，进入旁支边
    -> 沿旁支边前进到第二个转弯点
    -> 停车
    -> 执行第二次特定转弯
    -> 重新进入原来道路的反方向
    -> 从恢复前进状态继续任务
```

这里的两次转弯不能被压缩成一段任意弧线。每次转弯都必须有：

- 固定的路口/转弯点；
- 进入道路和目标道路；
- 目标航向；
- 入口检查；
- 车身扫掠检查；
- 完成条件；
- 失败后的安全停止状态。

当前局部搜索没有表达这两个连续转弯，也没有记录中间旁支边已经被借用但尚未完成第二次转弯。

### 5.5 十字路口没有按两个丁字路口处理

按照已经确定的规则，十字路口不应被当成“从当前点任意挑一条相邻边”。它应当拆成两个连续的丁字路口逻辑，根据阻塞边和当前进入方向产生三个合法恢复方向。

期望的候选应具有明确语义，例如：

```text
候选 A：沿当前边退到十字路口，左侧丁字逻辑，进入左侧边
候选 B：沿当前边退到十字路口，右侧丁字逻辑，进入右侧边
候选 C：沿当前边退到十字路口，组合两次转弯，进入原路反向或对向边
```

候选数量必须由道路拓扑和阻塞情况决定。对于已经被障碍锁存的物理边，正向和反向都必须被禁止。当前代码虽然可能枚举出多个共享锚点的相邻车道，但这些候选没有携带上述动作序列，因此不能作为十字路口规则已经实现的证据。

### 5.6 转弯中遇到障碍没有实现专用恢复流程

用户确定的特殊情况是：

```text
已经开始 90 度转弯
    -> 前方发现障碍
    -> 先完成当前转弯
    -> 到达转弯后的转弯点
    -> 倒车转回原来车道
    -> 再按丁字路口规则处理
```

当前代码会区分预期的转弯障碍和异常障碍。如果障碍被判断为异常，控制器可能直接结束当前转弯动作并进入姿态恢复。进入姿态恢复时会重置当前 maneuver，再从当前位姿启动局部搜索。

这会产生两个问题：

1. 当前车辆可能还没有到达转弯后的合法转弯点；
2. 后续恢复搜索不知道当前 90 度转弯已经进入了哪条边，也不知道原始道路是哪一条。

因此必须增加 `TURN_RECOVERY_AFTER_COMPLETION` 专用状态，或者让正常转弯动作先返回一个结构化的“转弯已完成但需要恢复”结果，再由避障状态机接管。

## 6. 目标避障动作模型

### 6.1 基本对象

后续避障实现应使用地图拓扑对象，而不是只使用几何出口：

| 对象 | 含义 |
|---|---|
| `blocked_lane` | 障碍所在的物理道路边，双向都被锁存 |
| `incoming_lane` | 障碍发生前车辆所在道路边 |
| `junction_id` | 本次恢复使用的路口 |
| `junction_type` | `T` 或 `X` |
| `turn_point` | 车辆可以开始特定转弯的合法点位 |
| `entry_heading` | 进入转弯点时道路方向 |
| `target_lane` | 本次恢复要进入的道路边 |
| `target_heading` | 进入目标道路后的恢复航向 |
| `template_id` | 90 度转入、掉头返回、十字路口组合等模板 |
| `obstacle_revision` | 本次障碍快照版本 |
| `ordinary_count` | 恢复后正常前进的普通节点计数起点 |

### 6.2 目标恢复状态机

```text
NORMAL_FOLLOWING
    │ 前方障碍确认
    ▼
OBSTACLE_BRAKING
    │ 锁存多边形、阻塞边和当前 pose
    ▼
RECOVERY_CLASSIFY
    │ 判断当前边、最近合法路口、T/X 类型、是否处于转弯中
    ▼
RECOVERY_CANDIDATES
    │ 生成有限个拓扑模板
    ▼
RECOVERY_GLOBAL_EVALUATION
    │ 总控只读评估候选出口后的任务路线
    ▼
RECOVERY_EXECUTING
    │ 执行选定模板
    ├─ RETREAT_TO_TURN_POINT
    ├─ TURN_INTO_BRANCH
    ├─ ADVANCE_TO_SECOND_TURN_POINT
    ├─ TURN_BACK_TO_ORIGINAL_LANE
    └─ RESUME_FORWARD
    ▼
RECOVERY_COMPLETE
    │ 报告真实出口、道路和航向
    ▼
NORMAL_REPLANNING
    │ ordinary_count 从恢复前进状态重新计算
    ▼
NORMAL_FOLLOWING
```

任意执行阶段发生以下情况时，必须停车并结束本次执行，不得用无限重试掩盖问题：

- 车身扫掠碰撞检查失败；
- 障碍版本过期；
- 当前道路或出口被重新标记为阻塞；
- 当前位姿离开允许的道路包络；
- 连续若干周期没有有效进展；
- 无法确认车辆已经到达指定转弯点。

### 6.3 候选生成规则

候选生成必须先确定道路拓扑，再生成运动动作：

```text
输入：当前 pose、当前行驶边、障碍多边形、障碍版本、地图拓扑

1. 将障碍多边形投影到地图道路边，得到 blocked_lane。
2. 找到车辆当前所在 incoming_lane。
3. 根据车头方向和道路几何，确定障碍前方的合法恢复方向。
4. 找到满足车身安全包络的最近合法 junction。
5. 判断 junction 是 T 还是 X。
6. 根据 junction 类型生成固定模板候选。
7. 删除使用 blocked_lane 或其他阻塞边的候选。
8. 为每个候选确定 turn_point、target_lane、target_heading。
9. 将候选交给总控做任务路线可行性评估。
```

生成候选时不能以“距离障碍更远”作为唯一目标。候选必须能够到达合法转弯点并完成明确的道路动作。

### 6.4 倒车动作约束

长距离倒车只允许在 `RECOVERY_EXECUTING` 的 `RETREAT_TO_TURN_POINT` 状态出现。

它必须满足：

- 当前存在已经锁存的障碍事件；
- 当前倒车属于该障碍事件的恢复模板；
- 倒车目标是明确的路口转弯点；
- 倒车过程中不进入被阻塞边的危险区域；
- 每个控制周期检查车身扫掠和障碍距离；
- 方向切换前停车确认；
- 到达转弯点后停车确认，不能一边倒车一边直接切入另一条道路；
- 正常路线跟随和正常转弯不得调用该长距离倒车状态。

正常转弯内部可能存在短距离入口修正，但它不应被统计为避障长距离倒车，也不应触发障碍恢复模板。

### 6.5 T 字路口模板

#### 模板 T-90：退到路口后转入另一条边

```text
T90_START
    -> BRAKE_AND_VALIDATE
    -> RETREAT_TO_TURN_POINT
    -> STOP_AT_TURN_POINT
    -> TURN_INTO_TARGET_LANE
    -> ALIGN_WITH_TARGET_LANE
    -> RESUME_FORWARD
```

完成判据：

- 车辆已经在目标道路包络内；
- 目标航向误差达到正常转弯动作的入口/出口要求；
- 当前实际车道等于 `target_lane`；
- 控制器报告真实出口位姿。

#### 模板 T-U：通过旁支边完成掉头并返回原边反方向

```text
TU_START
    -> RETREAT_TO_FIRST_TURN_POINT
    -> STOP_AT_FIRST_TURN_POINT
    -> TURN_1_INTO_BRANCH
    -> ADVANCE_TO_SECOND_TURN_POINT
    -> STOP_AT_SECOND_TURN_POINT
    -> TURN_2_BACK_TO_ORIGINAL_LANE
    -> ALIGN_WITH_REVERSE_HEADING
    -> RESUME_FORWARD
```

第二次转弯完成之前，不能报告恢复成功。中间旁支边只属于恢复动作的借用道路，不能被全局任务进度标记为已覆盖。

### 6.6 X 字路口模板

X 字路口按照两个连续丁字路口处理。候选模板应根据当前进入方向和阻塞边产生三个可能出口：

```text
X_LEFT_EXIT
    -> RETREAT_TO_JUNCTION
    -> T-STYLE_LEFT_TURN
    -> RESUME_FORWARD

X_RIGHT_EXIT
    -> RETREAT_TO_JUNCTION
    -> T-STYLE_RIGHT_TURN
    -> RESUME_FORWARD

X_REVERSE_EXIT
    -> RETREAT_TO_JUNCTION
    -> FIRST_TURN_INTO_BRANCH
    -> ADVANCE_TO_SECOND_TURN_POINT
    -> SECOND_TURN_BACK_TO_OPPOSITE_DIRECTION
    -> RESUME_FORWARD
```

实际候选数量还要经过阻塞边、车身几何和全局任务路线评估。这里的“三个方向”表示动作模板的拓扑语义，不表示可以在道路中间任意生成三条几何轨迹。

### 6.7 90 度转弯中遇到障碍

该场景必须独立记录原转弯上下文：

- 原始路口 ID；
- 原始进入道路；
- 原始目标道路；
- 转弯开始时的到达航向；
- 当前转弯阶段；
- 转弯完成后应到达的转弯点；
- 障碍所在边。

目标流程：

```text
TURN_ACTIVE
    │ 检测到异常障碍
    ▼
TURN_FINISH_REQUIRED
    │ 先完成当前转弯，不切换到历史轨迹倒退
    ▼
POST_TURN_TURN_POINT
    │ 到达转弯后的合法转弯点并停车
    ▼
REVERSE_TURN_TO_ORIGINAL_LANE
    │ 倒车转回原来车道
    ▼
T_RECOVERY_CLASSIFY
    │ 按丁字路口动作选择 90 度或掉头模板
    ▼
RESUME_FORWARD
```

如果当前转弯无法安全完成，必须报告结构化失败和最后安全位姿，保持零速度，不能假装已经完成了当前转弯。

## 7. 控制器、总控和规划器的接口边界

### 7.1 控制器提供的信息

控制器应提供候选动作的运动执行信息：

- 恢复标识；
- 障碍版本；
- 当前真实 pose；
- `blocked_lane`；
- `incoming_lane`；
- 路口 ID 和类型；
- 模板 ID；
- 目标出口道路；
- 目标航向；
- 需要使用的转弯点；
- 候选涉及的借用道路；
- 预计动作序列摘要。

控制器负责执行局部动作、检查实际车身安全和回报真实完成结果。

### 7.2 总控提供的信息

总控负责：

- 当前任务层；
- 已完成任务点、隧道和道路；
- 阻塞边快照；
- 普通节点计数；
- 候选出口之后的只读路线评估结果；
- 选中的模板和候选编号；
- 恢复完成后的全局重新规划。

总控不能只通过状态字符串猜测恢复动作已经完成，应该使用结构化字段判断动作阶段和结果。

### 7.3 规划器的边界

规划器只回答：

```text
如果从这个恢复出口、这个方向、这个任务进度继续，
是否仍然有合法路线完成当前任务？
```

规划器不回答：

```text
车辆应该倒车多少米？
什么时候开始转弯？
车身扫掠是否安全？
是否已经完成某个特定转弯动作？
```

这些问题属于控制器恢复动作执行。

## 10. 验收场景

避障动作改造至少需要用以下短场景验证。短场景只验证恢复动作，不用完整任务跑通来替代局部证据。

### S0：直路障碍，丁字路口 90 度恢复

验证：

- 障碍锁存；
- 倒车到路口转弯点；
- 停车后执行一次特定转弯；
- 进入另一条未阻塞道路；
- 正常前进恢复。

必须记录：实际倒车距离、转弯点 ID、目标道路、转弯完成时航向和恢复后的路线 ACK。

### S1：丁字路口掉头返回原道路反方向

验证：

- 第一次转弯进入旁支边；
- 到达第二个转弯点；
- 第二次转弯回到原道路反方向；
- 两次转弯之间不被错误报告为完成；
- 旁支边不被任务进度标记为已覆盖。

### S2：十字路口三方向候选

分别验证左侧、右侧和反向候选。每次阻塞一个或多个道路，检查：

- 候选数量是否由拓扑决定；
- 阻塞物理边的两个方向是否都被禁止；
- 选中候选是否经过全局任务可行性评估；
- 没有可行候选时是否安全停车。

### S3：正常 90 度转弯中发现障碍

验证：

- 当前转弯上下文被保存；
- 当前转弯先完成；
- 到达转弯后的转弯点；
- 倒车转回原来车道；
- 再按丁字路口规则选择恢复方向；
- 不直接进入历史 breadcrumb 退回链。

### S4：长距离恢复

将障碍放在距离最近转弯点超过当前 `0.85 m` 局部范围的位置，验证：

- 可以沿当前边连续、安全地倒车到合法转弯点；
- 不在道路中间提前改变道路方向；
- 不因固定局部半径直接误报无候选；
- 倒车只在障碍恢复状态发生。

### S4.1：倒车到位但姿态偏离时的回中

单独构造以下情况：车辆可以安全倒车到转弯点附近，但车身横向偏离道路中心或航向存在明显误差。验证：

- 控制器不会直接开始特定转弯；
- 如果倒车中有安全空间，可以边倒车边闭环修正；
- 如果倒车结束后仍偏离中心，可以短距离前进完成回中；
- 向前回中不是固定动作，而是由实时姿态误差和安全空间决定；
- 回中完成后才停车确认并进入转弯；
- 回中轨迹始终留在当前合法道路包络内；
- 不通过历史轨迹回放或固定速度序列假设车辆已经入位。

仿真记录必须同时保存：

- 实际 pose 轨迹；
- `/cmd_vel_nav` 线速度和角速度；
- 道路中心横向误差；
- 进入航向误差；
- 到达转弯点误差；
- 每个动作阶段的开始和结束时间；
- 车身扫掠和碰撞保护结果。

以下轨迹不能通过验收：

```text
还没有到转弯点就切入相邻道路
到达转弯点但横向/航向误差未收敛就开始转弯
通过固定回放动作碰巧到达目标点
碰撞保护拦截后仍把轨迹标记为成功
```


在没有障碍的正常路线和正常转弯中记录实际线速度符号，确认：

- 正常直行不会进入恢复倒车状态；
- 正常转弯内部的短入口修正不被记录为长距离避障倒车；
- 普通路线不会调用恢复模板。

### S6：恢复后的 RFID 和普通节点计数

验证：

- 恢复动作本身不伪造 RFID 完成；
- 恢复完成后从真实出口进入正常路线；
- 普通节点计数从恢复前进状态重新开始；
- 经过 RFID 时仍停车、位置校正和按条件播报；
- 两个普通节点之后仍然必须进入 RFID 超节点。

### S7：三层任务交接

分别在第一层任务、第二层隧道和第三层道路覆盖中触发障碍，验证：

- 当前层未完成目标保持未完成；
- 已完成目标不会重复伪造；
- 被阻塞道路保持 skipped；
- 后续路线仍按当前层继续；
- 所有任务和道路完成后才返航回家。

## 11. 通过标准

一次避障恢复只有同时满足以下条件才能报告成功：

1. 障碍版本和恢复标识仍然有效；
2. 使用了具有明确道路语义的恢复模板；
3. 所有长距离倒车都发生在障碍恢复状态；
4. 倒车终点是合法路口转弯点，而不是任意几何位置；
5. 每次特定转弯都有明确入口、目标道路和完成条件；
6. 车辆全车身轨迹没有碰撞保护介入；
7. 执行过程中没有无界方向切换；
8. 最终真实 pose 位于目标道路安全包络内；
9. 控制器报告真实 `resume_lane`、`resume_node` 和 `resume_heading`；
10. 总控重新规划并收到路线 ACK；
11. 恢复动作没有伪造任务点、隧道或道路覆盖进度；
12. 正常路线恢复后，RFID 和普通节点计数继续按原规则工作。

以下情况不能算成功：

- 只到达一个几何出口，但没有完成规定转弯；
- 只因为离障碍变远就认为恢复成功；
- 碰撞保护拦截了危险命令后仍报告完成；
- 用增加重试次数掩盖没有进展；
- 用修改正常控制参数扩大容差后把错误轨迹判为通过；
- 候选评估返回 `PARTIAL` 就直接当作局部动作完成。

## 12. 当前阶段结论

Contrast 侧已经完成本记录定义的恢复动作改造。当前执行链为：

```text
障碍刹停并锁存
    -> 拓扑候选（t_junction_* / x_junction_*）
    -> RETREAT_TO_TURN_POINT
    -> 停车确认和方向切换保护
    -> CAPTURE（转弯点再次确认停车）
    -> APPROACH_ENTRY
    -> TURN_60
    -> DIAGONAL_CREEP
    -> TURN_30
    -> POSE_RECOVERY_COMPLETE
    -> 总控按真实出口重新规划并等待路线 ACK
    -> FOLLOWING
```

恢复计划只在独立 `contrast_navigation_core` 中生成。它保存合法路口锚点、出口道路和目标航向；控制器先沿实时锚点闭环倒车，到达转弯点附近后发布零速度并确认停车，再一次性启动 Contrast 的 `TurnManeuverController`。该控制器严格执行 `CAPTURE -> APPROACH_ENTRY -> TURN_60 -> DIAGONAL_CREEP -> TURN_30 -> COMPLETE`，恢复控制器不再用 `TURN_INTO_EXIT` 的目标跟踪反馈自行合成弧线。对外保留 `POSE_RECOVERY_ALIGN_FOR_TURN` 作为停车捕获阶段的兼容状态名，它不执行独立的回中或原地画弧动作。

严格动作输出的每个非零命令都重新进行车辆全身扫掠检查；暂停、定位无效、动作失败、目标转角不属于单次固定动作或扫掠不安全时立即发布零速度并进入故障保护。倒车扫掠被阻断时仍先停车，再按实时锚点方向执行一次有界前进调整；调整同样经过车身扫掠检查，随后重新闭环倒车。

本次严格 loopback 验收目录为 `/tmp/contrast_strict_turn_all_final`，六场全部通过：

- `south_nominal`、`north_mirror`：南北向对称直路障碍恢复；
- `south_yaw_plus6`、`south_yaw_minus6`：起始航向扰动；
- `south_less_space`：较小障碍间距；
- `after_normal_90deg_turn`：正常 90° 转弯后再遇障碍。

六场均记录了 `POSE_RECOVERY_BRAKING -> POSE_RECOVERY_SELECTING -> POSE_RECOVERY_RETREAT_TO_TURN_POINT -> POSE_RECOVERY_DIRECTION_STOP -> POSE_RECOVERY_ALIGN_FOR_TURN -> POSE_RECOVERY_TURN_INTO_EXIT -> POSE_RECOVERY_COMPLETE`，没有协议错误、FAULT 或碰撞保护拦截；严格动作完成后每场恢复后实测连续直行均超过 `0.20 m`，距离范围为 `0.20040–0.20073 m`。

生产 `visual_navigation` 和 `navigation_mission_manager` 回归测试分别为 18/18、2/2；Contrast 包测试为 3/3。现有 Contrast YAML 中的 `recovery_linear_speed`、`recovery_angular_speed`、`recovery_primitive_s`、`recovery_max_radius`、`recovery_max_expansions` 和 `recovery_selection_timeout_s` 保持原值。后续若要扩大到更多地图拓扑或实车制动距离，应新增场景证据，不应修改正常直行、正常转弯或生产控制器参数来放宽判据。

本记录第 4、5 节保留了 coding 前的行为差异，作为为什么需要改造的基线；当前实现和实际验收结果以本节及 [`POSE_RECOVERY_VALIDATION_REPORT.md`](../src/contrast_controller/POSE_RECOVERY_VALIDATION_REPORT.md) 为准。
